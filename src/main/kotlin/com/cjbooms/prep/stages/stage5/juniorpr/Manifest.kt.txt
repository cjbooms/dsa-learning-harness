STAGE 5 ANSWER KEY — do not open until your 25-minute cold review is done.
Planted issues, in severity order:

SEVERE
1. RACE on refreshCount (startBackgroundRefresh): Session.refreshCount is a
   plain var mutated from a background thread while other threads may read/
   hold the Session. No synchronization, no volatile — lost updates AND a
   visibility problem. ConcurrentHashMap makes the MAP safe, not the VALUES.
   This is the "thread-safe components don't compose" lesson.
2. RESOURCE LEAK under exception (audit): FileWriter is opened/closed per
   call with no try/finally (or .use). If write() throws, the file handle
   leaks. Under failure, audit() ALSO propagates and can kill the background
   thread silently (see #3). Fix direction: .use {}, buffered appender, or a
   proper logger.
3. BACKGROUND THREAD DIES SILENTLY: the refresh loop has no error handling;
   one exception (e.g. from a future change, or an interrupt) terminates the
   daemon thread and sessions simply stop refreshing — no signal. Also no
   shutdown mechanism at all: `while(true)` on a daemon is a leak pattern.

MEDIUM
4. WRONG IDLE SEMANTICS (evictIdleSessions): "idle" is measured from
   createdAt, not last activity. Active sessions created long ago get evicted
   — a correctness bug against the stated business goal ("evict IDLE
   sessions"). Anchor your finding here: the goal says idle, the code says age.
5. lastEvictionReport write is unsynchronized (visibility): written in
   evictIdleSessions, read via evictionReport() from any thread — may never
   be seen. Minor alone, but it's the SAME class of bug as #1 — group them
   when narrating ("a pattern of unsynchronized shared state").

TRIVIAL (group as one line in narration)
6. audit() opens/closes a file per call — O(syscalls) per event; a logger or
   single appender would do. Also timestamps twice (message + call site).
7. getSession exposes the mutable Session directly — callers can mutate
   refreshCount/token freely, undermining encapsulation (API design).
8. No validation: empty userId/token accepted silently.

SCORING: 1, 4, 2 are the three to lead with (data race, wrong business
semantics, resource/error handling). Finding 5 AND 1 and naming them as one
pattern is the depth-over-breadth move.
